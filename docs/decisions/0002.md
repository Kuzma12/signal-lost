# 0002: Track visited rooms in Game and draw the map from fixed grid positions

- **Status:** Accepted
- **Date:** 2026-11-21
- **Round:** 2
- **Related requirements:** R4 (Ship Map), R5 (Room Scanner); AC-R4.x and
  AC-R5.x in `spec.md` Section 6

## Decision (Y-statement)

In the context of **adding a `map` command that shows only the rooms the
player has visited and marks where they are now, plus a `scan` command that
gives each room's clue, without breaking the Round 1 rule that `game.py`
holds the rules and `cli.py` holds all the text (ADR 0001)**,

facing **the need to remember where the player has been, to draw rooms in
positions that match how they really connect, to keep unexplored rooms
hidden, and to fit everything inside the 50-column layout, while keeping
both commands free and the game deterministic**,

we decided for **a `visited` set on `Game` (starting with the Cryo Bay and
updated only inside `Game._move()`), passed to the CLI as a `frozenset`
snapshot on every `TurnResult`; a fixed `MAP_GRID` of (row, column)
positions in `world.py`, with a test that every exit joins grid neighbors;
a `clue` field on each `Room`; and an ASCII grid drawn by
`cli.render_map()` using 11-character cells and short labels, so four
columns fill exactly 50 characters**,

and neglected **working out room positions automatically from the exits
at run time; a plain list of visited rooms with no layout; storing a short
map label or clue table in `cli.py` or `game.py`; and showing `?` hints for
unexplored exits**,

to achieve **a map that looks like the ship and is checked against the real
exits, a single place where "visiting" happens (so later lock or hazard
checks in `_move()` can't get out of step with the map), map and scan
commands that change no game state and cost no oxygen, and output that is
identical every run and can be tested exactly**,

accepting **that grid positions and short labels must be kept in line with
the room table by hand when the map changes (the grid-neighbor test catches
mistakes in positions), that `cli.py` reads static map data from
`build_ship()` to draw links, and that labels are limited to 8 characters to
fit the 50-column frame**.

## Consequences

- `Game.handle` gains two handlers (`_map`, `_scan`) and two outcomes
  (`MAPPED`, `SCANNED`), following the "one parser rule, one handler, one
  render branch" pattern from ADR 0001.
- `TurnResult.visited` is a `frozenset`, so a result stays correct even
  after the game moves on, and the CLI can't change game state through it.
- A future save/load feature must also save `visited` (as a list of room
  ids) alongside `room_id`, `oxygen`, and `status`.
- Changing the ship layout in a later round means updating `MAP_GRID` and
  the cli map labels. The tests in `test_world.py` and `test_cli.py` fail
  if they disagree with the exits or the 50-column width.
