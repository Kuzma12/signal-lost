# 0001: Keep game rules separate from terminal I/O

- **Status:** Accepted
- **Date:** 2026-11-21
- **Round:** 1
- **Related requirements:** R1, R2, R3 (and AC-G.4 in `spec.md`)

## Decision (Y-statement)

In the context of **building Signal Lost as a terminal text adventure that
must be checked by automated `unittest` tests and extended over several
rounds**,

facing **the need to test movement, oxygen, and win/loss rules (including
full playthroughs and edge cases like Ctrl-D) without a person typing at a
real terminal, while leaving room for inventory, hazards, puzzles, and
save/load later**,

we decided for **a pure `Game` class in `game.py` that takes a parsed
`Command` and returns a structured `TurnResult` (outcome, room, oxygen,
oxygen used) and never prints or reads input, plus a separate `cli.py` whose
`run(input_fn=input, output_fn=print)` handles all text and accepts
replacement input/output functions**,

and neglected **a single loop that mixes `input()`, `print()`, and the rules
together, and testing that loop by patching `builtins.input`/`sys.stdout` or
driving it through a subprocess only**,

to achieve **fast, deterministic tests of the rules with no terminal; exact
checks of what the player sees by passing in a scripted input list and an
output collector; and a clear place to add future commands (one parser rule,
one handler, one render branch) without rewriting the game loop**,

accepting **a little more code up front (the `Command`, `TurnResult`, and
`Outcome` types, plus a render function that maps each outcome to text) and
the discipline of never putting game rules in `cli.py` or output in
`game.py`**.

## Consequences

- `tests/test_game.py` checks every rule by calling `Game.handle()` directly.
- `tests/test_cli.py` plays whole games through `run()` with a fake
  `input_fn` that raises `EOFError` or `KeyboardInterrupt` to simulate
  Ctrl-D and Ctrl-C.
- A static test parses `game.py` with `ast` and fails if it ever calls
  `print()` or `input()`, so the separation can't quietly erode.
- Two end-to-end tests still run `python3 main.py` in a subprocess, to
  confirm the real entry point works.
- Later rounds can add a save/load feature by serializing the plain fields
  on `Game` (`room_id`, `oxygen`, `status`) without touching the CLI.
