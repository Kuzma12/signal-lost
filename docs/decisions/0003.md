# 0003: Keep starting items on Room and track item movement on Game

- **Status:** Accepted
- **Date:** 2026-11-21
- **Round:** 3
- **Related requirements:** R6 (Collecting Items), R7 (Inventory System);
  AC-R6.x and AC-R7.x in `spec.md` Section 6

## Decision (Y-statement)

In the context of **adding items that the player can see in rooms, pick up
with `take`, list with `inventory`, and leave behind with `drop`, while
keeping the Round 1 split between rules in `game.py` and text in `cli.py`
(ADR 0001) and the read-only world data from Round 2 (ADR 0002)**,

facing **the need for items to move between rooms and the inventory during
play without changing the shared ship data, for every item to be in exactly
one place at all times, for typed names like `TAKE  Repair Kit` to match
reliably, and for all three commands to cost no oxygen and stay
deterministic**,

we decided for **an immutable `items` tuple on each frozen `Room` that
records only where items start; a `room_items` dict of lists and an
`inventory` list on `Game`, seeded from `Room.items` in a new game, as the
only state that changes when items move; three handlers (`_take`, `_drop`,
`_inventory`) that move an item by removing it from one list and appending
it to the other; tuple snapshots of the current room's items and the
inventory on every `TurnResult`; and exact matching on the full item name
after the parser lower-cases it and collapses spaces**,

and neglected **making `Room` mutable and editing its items in place;
storing items on a separate global registry or as `Item` objects with
descriptions and effects; tracking each item's location in a single
`item -> place` map; and partial or single-word name matching
(`take kit`)**,

to achieve **a ship built by `build_ship()` that never changes during play,
so each `Game` gets its own item state; item conservation that can be
tested after any sequence of commands (always the same four items across
rooms and the inventory); a predictable inventory order (pickup order) and
room order (starting order, then drops appended); take, drop, and inventory
commands that change nothing but item locations; and output the CLI renders
from the result alone, without reaching into `Game`**,

accepting **two places that describe items (the static starting placement on
`Room` and the live state on `Game`), list-based membership checks that are
fine for four items but would need a different structure for many, and
players having to type multi-word names in full**.

## Consequences

- `Game.handle` gains `take`, `drop`, and `inventory` handlers and the
  outcomes `TAKEN`, `NOT_HERE`, `DROPPED`, `NOT_CARRIED`, `INVENTORY`,
  following the "one parser rule, one handler, one render branch" pattern.
  A take or drop with no name returns `INVALID`, and the CLI answers
  `Take what?` / `Drop what?` based on the command kind, just as a bad
  `go` gets `Go where?`.
- `cli.render_room` takes an optional `items` argument and adds an
  `Items here:` line only when the room has items, so empty rooms still
  match the Round 1 display format exactly.
- Items have no effect on movement or oxygen in Round 3. A future
  locked-door rule can check `Game.inventory` inside `Game._move()`, which
  is still the only place movement happens.
- A future save/load feature must also save `room_items` and `inventory`
  (as lists of names) alongside `room_id`, `oxygen`, `status`, and
  `visited`. `Room.items` comes from `build_ship()` and does not need saving.
