# 0006: Save the game as checked JSON through a file-only module

- **Status:** Accepted
- **Date:** 2026-11-22
- **Round:** 6
- **Related requirements:** R11 (Saving the Game), R12 (Loading the Game);
  AC-R11.x and AC-R12.x in `spec.md` Section 6, design in Section 3.12

## Decision (Y-statement)

In the context of **letting the player type `save` to write their
progress to a JSON file and `load` to restore it, where the save must hold
the room, oxygen, health, inventory, items left in rooms, visited rooms,
and the pod lock, a missing save must be reported instead of crashing, and
a damaged save must not lose current progress, while keeping rules in
`game.py` and text in `cli.py` (ADR 0001), read-only world data (ADR
0002), live item state on `Game` (ADR 0003), and the single turn order in
`Game._move()` (ADRs 0004, 0005)**,

facing **a test that forbids `print()` and `input()` in `game.py`; the
need for tests that never write a save file into the project; save files
that can be cut off, not JSON, or edited by hand into states the rules
can never reach (99 oxygen, two keycards, standing inside the pod); the
risk of a load that fails half-way and leaves a mix of old and new state;
the risk of a save that fails half-way and destroys the previous save;
the standard-library-only rule; and the Round 1 rule against building for
features nobody asked for yet**,

we decided for **a new module, `signal_lost/savefile.py`, that only knows
files and JSON (`write(path, data)` writes a temporary file and moves it
into place with `os.replace`; `read(path)` raises `NoSaveFile` or
`DamagedSave`), with no imports from the game; `save` and `load` as
ordinary commands in the parser and in `Game.handle`'s `kind -> method`
table, so the rules for what is saved and what is valid stay in
`game.py`; `Game.save_data()` building a plain dict with a `version`
number, in which every room's item list and the sorted visited rooms are
written out, and nothing from `build_ship()` is; a full check of a loaded
file (exact keys, version 1, status `playing`, oxygen 1-12, health 1-10,
known rooms, never in or having visited the pod, every room listed, each
item in exactly one place with only the medkit allowed missing, a boolean
lock) that runs completely before one combined assignment replaces the
state; a `save_path` on `Game` and `cli.run()`, defaulting to
`signal_lost_save.json` in the current folder, so tests pass temporary
folders; and five new outcomes (`SAVED`, `SAVE_FAILED`, `LOADED`,
`NO_SAVE`, `DAMAGED_SAVE`), rendered by `cli.py` with `LOADED` showing
the restored room display**,

and neglected **doing file I/O in `cli.py` and handing the data to `Game`
(the CLI would have to decide what a valid save is, which is a rule);
putting the checks in `savefile.py` (it would have to import game
constants, and `game.py` imports it); `pickle` (not human-readable, and
loading an untrusted pickle can run code); saving the whole `Game` object
or the room data (the map is fixed and comes from `build_ship()`); a
basic check of only JSON syntax and key types (the user chose a full
check, and a weaker one lets hand-edited files load impossible states);
assigning fields one by one while checking them (a late failure would
leave a half-loaded game); several or named save slots, asking before
overwriting, auto-save, or loading at start-up (the user chose one slot
that is overwritten without asking, and R11/R12 ask for none of the
rest); a save in the home folder or next to `main.py` (the user chose the
current folder); and one-letter aliases (`s` is south, `l` is look)**,

to achieve **save and load that cost no oxygen or health and never touch
`_move()` or the turn order; a loaded game that plays exactly like the
game that was saved (tested by saving at every step of a winning script
and replaying the rest in a new game); a load that is all-or-nothing, so
a missing or damaged file leaves every part of the current game as it
was; a save that can't destroy the previous save; a file format a person
can read, with a version number; output that `cli.py` renders from the
outcome alone, as in ADRs 0001-0005; and tests that never write into the
project**,

accepting **that `game.py` now reaches the file system indirectly
through `savefile` (it still never prints or reads input); that the check
code in `game.py` (`_check_save`) must be updated whenever new game state
or items are added; that the checks reject only impossible states, so a
hand-edited file that describes a reachable state (for example, an
earlier point with more oxygen) still loads, which R12 allows anyway;
that a save made by a future version with a different `version` number is
reported as damaged; and that the save file goes to whatever folder the
game was started from**.

## Consequences

- `parser.py` gains two words, `save` and `load`, with no aliases.
  Anything after them (`save game`) is an unknown command.
- `Game` gains `save_path`, `save_data()`, `_check_save()`, and the
  `_save` / `_load` handlers. `TurnResult` is unchanged; a `LOADED` result
  carries the restored room, oxygen, health, and items.
- `cli.render_result` gains five branches; `help` lists `save` and `load`;
  `run()` takes `save_path`.
- `.gitignore` ignores `signal_lost_save.json` and its `.tmp` file.
- Any new piece of game state in a later round must be added to
  `save_data()`, to `_check_save()`, to the `full_state()` helper in
  `tests/test_game.py`, and to spec Section 3.12. It also needs a decision
  on whether old saves (version 1) are still accepted.
