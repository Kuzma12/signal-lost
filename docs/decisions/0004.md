# 0004: Apply hazard damage inside the move and check health before winning

- **Status:** Accepted
- **Date:** 2026-11-21
- **Round:** 4
- **Related requirements:** R8 (Health and Hazards), R9 (Medkit Healing);
  AC-R8.x and AC-R9.x in `spec.md` Section 6

## Decision (Y-statement)

In the context of **adding a health system where the Reactor Core and the
Cargo Hold cost 2 health on every entry, health 0 ends the game, and a
carried medkit can be used once to heal, while keeping rules in `game.py`
and text in `cli.py` (ADR 0001), read-only world data (ADR 0002), and live
item state on `Game` (ADR 0003)**,

facing **the need for a single, testable turn order now that one move can
change oxygen and health together (and can empty both at once), for the
world to say which rooms are dangerous without knowing about health, for
the first item that is used up rather than moved, and for all output to
stay inside 50 columns**,

we decided for **a `hazard` flag on each frozen `Room` (set from a
`HAZARD_ROOMS` constant in `world.py`), with the damage amount
(`HAZARD_DAMAGE = 2`), `STARTING_HEALTH = 10`, and `MEDKIT_HEALING = 4` as
rule constants in `game.py`; a `health` field on `Game`; applying damage
inside `Game._move()` straight after the oxygen cost, then checking health
0 (new outcome `DIED`, status `LOST`) **before** the win and oxygen checks;
a generic `use <item>` command whose handler checks "carried?" first, then
"is it the medkit?", then "already at full health?" before healing and
removing the medkit; and `health`, `damage`, and `healed` on every
`TurnResult` so the CLI can show a separate health gauge line, a
room-specific hazard message, and the death ending from the result
alone**,

and neglected **a hazard hook that runs after the move as a separate step
(it could drift out of step with `_move()`, the one place that changes
rooms); a numeric damage field on `Room` (puts a game rule in the world
data); checking oxygen first so a double zero shows the oxygen ending;
reusing the `LOST` outcome with a separate "cause" field; a dedicated
`heal` command or a medkit-only parser rule; and showing health on the
oxygen gauge line**,

to achieve **one function that fully decides what a move does, so a player
on move 12 with 2 health who enters a hazard always gets the same, tested
ending (the health ending, as the user chose); hazards that can be moved
or added by editing one constant; a `use` verb that reports clear,
different messages for every case and leaves room for other items to gain
uses later without new parsing; item conservation that still holds for
everything except a used medkit; and 50-column output**,

accepting **that with 12 oxygen and 2 damage per hazard, health can only
reach 0 on move 12 (when oxygen also runs out), so the health ending only
shows up because health is checked first; that "item never lost" (AC-R7.7)
now needs an exception for a used medkit (AC-R9.7); and that
`render_room` draws the health line only when `health` is passed, so a new
caller that forgets it silently loses the gauge (tests check every real
display has it)**.

## Consequences

- `Game.handle` gains a `use` handler and the outcomes `DIED`, `HEALED`,
  `FULL_HEALTH`, and `CANT_USE`. Using an item that isn't carried reuses
  `NOT_CARRIED`, and a bare `use` returns `INVALID` (the CLI answers
  `Use what?`), following the take/drop pattern from ADR 0003.
- The three move endings (`MOVED`, `WON`, `LOST`, now `DIED`) render
  through one path in `cli.render_result`, using a small outcome to
  ending-text table.
- Future locked doors or new hazards still belong in `Game._move()`. Any
  lock check should come before the room changes, and therefore before
  damage, so a locked hazard room never hurts the player.
- A future save/load feature must also save `health`, alongside `room_id`,
  `oxygen`, `status`, `visited`, `room_items`, and `inventory`. A used
  medkit is simply absent from both item collections, so no extra state is
  needed for it.
